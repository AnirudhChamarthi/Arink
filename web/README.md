# Riskbot v2 — web UI

React + TypeScript single-page app over the Riskbot REST API (`/v2`, CONTRACT.md 6.1). It lets an analyst
pick one of the three risk questions, start from a sample or uploaded dataset, edit the variation plan
within the model catalogue, follow the run, compare variations, inspect the working behind every number,
adjust the qualitative assessment (clearly labelled *judgment*), sign off and download the report.

## Run it

Requires Node 22 / npm 10.

```bash
cd web
npm install

# Against the API (default base URL http://localhost:8000/v2; CORS allows http://localhost:5173)
npm run dev
VITE_API_BASE=http://my-host:8000/v2 npm run dev

# Mock mode: no backend; the browser serves the contract fixtures and simulates the run lifecycle
npm run dev:mock            # same as VITE_MOCK=1 npm run dev

npm test                    # vitest + testing-library (jsdom)
npm run build               # type-check (tsc -b) + production bundle in dist/
npm run sync:fixtures       # re-copy ../riskbot/contract/generated/{fixtures,schema} into src/mocks/
```

| Variable | Default | Meaning |
|---|---|---|
| `VITE_API_BASE` | `http://localhost:8000/v2` | REST base URL |
| `VITE_MOCK` | unset | `1` = in-browser mock API backed by the fixtures |

In mock mode a run created from any dataset goes `pending → running → awaiting_review` in about five
seconds; a dataset whose name contains "fail" ends in `failed`. Three fixture runs (`run-0001..3`) are
pre-loaded. Fixture numbers are placeholders from the contract fakes — shapes are exact, values are not.

## Screens

| Route | Screen |
|---|---|
| `/` | **Questions** — the three questions (`GET /questions`) with a summary of each default plan (grid model, dimensions, fixed values, extras). Load the sample dataset (`GET /samples/{q}`) or upload JSON; the dataset is validated by `POST /datasets/validate` and findings are grouped by severity. Recent runs table. |
| `/new/:question` | **Plan editor** — every parameter of the grid model from the catalogue (`GET /models?question=`): default / fixed / vary; choices as checkboxes, numeric values within min/max, `applies_when` conditions shown. Extra runs can be toggled and their parameters set. Live variation preview: cartesian product, distinct count after inapplicable parameters drop out (mirrors `resolve_params`), plan-limit check. Seed, max variations, `use_llm` (off by default). Submit → `POST /runs` → run page. |
| `/runs/:id/:tab?` | **Run** — status stepper and progress while polling `GET /runs/{id}` every 1.5 s until `awaiting_review / approved / rejected / failed`. Tabs: **Overview** (metric ranges with units, min/max linked to the producing trace, method spread, label counts, conclusion flips, break-evens, extra runs, verifier findings) · **Variations** (sortable, filterable params × labels × metrics table, error rows, per-model view) · **Sensitivity** (SVG tornado per metric from `comparison.sensitivity`, table view, range strip per metric) · **Assessment** (factor table: likelihood, impact, control, inherent, residual, rationale, evidence, source badge; edit form producing `FactorEdit` with a mandatory reason and a rating preview using the ported `rules.py`) · **Review** (approve / reject with reviewer and comment; disabled unless `awaiting_review`) · **Report** (headline, sign-off, markdown rendered safely, download `.md`) · **Audit log**. |
| `/traces/:traceId#step` | **Trace viewer** — numbered steps with KaTeX formula, substitution (KaTeX if it looks like LaTeX, plain text otherwise), value + unit, per-row tables, notes; inputs, assumptions, results, warnings; trace id and input hash with copy button. The target step is highlighted and scrolled into view. |

A synthetic-data banner appears wherever the dataset or run is synthetic. Every screen has loading, empty
and error states; API errors are shown as the contract `ErrorBody` (code, message, details).

## Architecture

```
src/
  api/
    types.ts       TypeScript mirror of riskbot/contract/types.py
    decoders.ts    runtime decoders (guards) for every contract type; reject unknown fields, fill defaults
    client.ts      RiskbotApi interface, fetch implementation, ApiError(ErrorBody), pollRun()
    context.tsx    ApiProvider + useAsync (loading / error / ready)
  mocks/
    mockApi.ts     in-memory RiskbotApi over the fixtures (status progression, Conflict/NotFound rules,
                   edits applied with the rating rules, audit log, report)
    derive.ts      mock-only: sensitivity + label counts derived from fixture variations
    fixtures/, schema/   copied from riskbot/contract/generated by `npm run sync:fixtures`
  lib/             format.ts (units), rules.ts (port of contract/rules.py), plan.ts (resolve_params,
                   variation counts, plan checks), markdown.tsx (safe renderer), draft.tsx, links.ts
  components/      ui.tsx (banners, states, badges, MetricValue → trace link), charts.tsx (SVG)
  screens/         Home, NewRun, RunPage (+ run/* tabs), TraceViewer (lazy-loaded with KaTeX)
```

- **Talks only to the REST API.** All calls go through `RiskbotApi`; the mock implements the same
  interface, so screens cannot tell the difference.
- **Types are checked against the contract three ways.** Decoder shapes are typed against `types.ts`
  (`tsc` fails on drift); `contract.test.ts` checks every decoder's field list and required set against
  the generated JSON Schemas, compares enums, and validates every fixture against both the JSON Schema
  (small in-test validator) and the decoder. Responses are decoded at runtime, so a backend drift
  surfaces as a readable error instead of a broken screen.
- **Every number is traceable.** `MetricValue` links to `/traces/{trace_id}#{trace_step}`; range min/max
  link to the variation that produced them.
- **No HTML injection.** Report markdown is rendered to React elements by a small renderer (raw HTML
  shown as text, only http(s)/mailto/relative links). The only `dangerouslySetInnerHTML` is KaTeX output
  (`trust: false`, `throwOnError: false`).
- **Bundles.** KaTeX is code-split into the trace screen; fixtures are only bundled in mock builds.
- **Accessibility.** Skip link, labelled controls, ARIA tabs with arrow-key navigation, `aria-sort` on
  sortable headers, live regions for status, focus styles, reduced-motion support, charts with accessible
  names plus table views. Light/dark themes from `prefers-color-scheme`, switchable in the header.
- **Styling.** Plain CSS with variables (`src/styles.css`); responsive from 1280 px laptops to tablets.

## Tests

`npm test` runs (jsdom, two workers):

- `api/contract.test.ts` — fixtures vs JSON Schemas vs decoders; field/required/enum parity; guards.
- `api/client.test.ts` — routes and bodies, ErrorBody errors, network/non-JSON failures, contract drift,
  polling stops on every settled status, 1.5 s default interval, abort.
- `lib/lib.test.tsx` — unit formatters, rating rules, variation counts, plan checks, safe markdown.
- `screens/screens.test.tsx` — questions list, sample validation, overview from a fixture, variations
  sorting/filtering/error rows, assessment edit → valid `FactorEdit`, review disabled unless
  `awaiting_review`, trace viewer renders KaTeX and escapes text.
- `smoke.test.tsx` — mock mode end to end: sample → plan → start run → awaiting_review → approve → report
  → audit log.

## Known limitations

- Currency symbols on run pages need the dataset currency (see `CONTRACT_REQUESTS.md` #1).
- Progress is indeterminate: the contract has no completed-variation counter (#4).
- The plan editor varies parameters of the default grid model; it does not switch grid models.
- Uploads are validated by the server; the client only checks JSON syntax and dataset `kind`.
